Ce que la migration ne touche pas

Les 183 actions metier restent telles quelles
Le design system remplace la presentation, pas le comportement. jrOuvrir, jsEnregistrer, stationView et les 180 autres ne sont pas concernes.

L'application declenche ses comportements par delegation : act('jrOuvrir', [id]) pose un data-action, et un ecouteur unique dans app.js resout le nom vers la fonction globale. C'est exactement la meme architecture que celle du design system, qui utilise data-pg-* pour ses propres comportements de presentation. Les deux couches ne se marchent pas dessus : l'une porte le metier, l'autre l'interface.

Le prefixe pg- est deja pris

Cinq classes existantes commencent deja par pg-
pg-anim, pg-tooltip, pg-tooltip__dot, pg-tooltip__row, pg-tooltip__title — l'infobulle de Chart.js.

Aucune ne collisionne aujourd'hui : le design system n'a ni pg-anim ni pg-tooltip (son infobulle s'appelle pg-tip). Mais elles disparaissent avec Chart.js, et il faut les retirer a ce moment-la : laisser deux familles pg- d'origines differentes dans la meme feuille, c'est programmer une collision silencieuse pour la prochaine version.

Variables CSS

Ne pas ecrire --color-primary: var(--action-primary-bg)
Le raccourci qui parait evident est celui qui casse tout en silence.

Les 75 variables existantes sont nommees par apparence (--color-primary, --color-accent). Celles du design system sont nommees par role (--action-primary-bg, --status-warning-text). Ce n'est pas une difference de vocabulaire : c'est une difference de cardinalite.

--color-primary apparait 31 fois dans les feuilles existantes, reparties sur color (12), background (7), border-color (3) et accent-color. Un alias unique donnerait au texte d'un lien la couleur du fond d'un bouton. Il faut donc remplacer chaque usage par le role correspondant, un par un — c'est mecanique, mais ca ne s'automatise pas.

Ce qu'il ne faut PAS adapter

Ne pas ecrire d'adaptateur pour les classes. Un .btn { @extend .pg-btn } ou une regle .btn, .pg-btn { ... } ferait tenir les deux systemes en meme temps, et personne ne saurait plus lequel s'applique. Les classes se remplacent dans le HTML genere, module par module.

Dans quel ordre

L'ordre n'est pas indifferent : il est choisi pour que chaque etape soit verifiable et annulable seule, et pour que la plus risquee arrive quand l'equipe connait deja le systeme.

Les utilitaires d'espacement

Decision : ils disparaissent au fil de la migration
Aucun equivalent n'est fourni, et il ne faut pas en recreer. 425 occurrences sur seize classes — mb-1..4, mt-1..6, gap-2..4, flex, flex-center, grow.

Un utilitaire decide l'espace au point d'appel : <div class="card mb-4">. Il y a 425 decisions de ce genre dans le code, et rien ne garantit qu'elles concordent — la meme carte porte mb-4 ici et mb-3 trois ecrans plus loin. C'est ainsi qu'une interface se defait : pas d'un coup, mais d'un ecart de quatre pixels a la fois.

Dans ce systeme, un bloc de niveau page sait de combien il s'ecarte du suivant. La regle est declaree une fois, dans base.css, et s'applique a dix-huit composants : 16 px entre deux blocs, 40 px entre deux sections, et zero en queue de conteneur. Rien a poser dans le balisage.

La marche a suivre

Ce n'est pas un chantier separe
Aucune passe de 425 corrections a programmer. La regle s'applique quand on touche un module de toute facon, en meme temps que le remplacement des classes. Un module converti ne contient plus d'utilitaire ; les modules pas encore touches gardent les leurs, et l'ancienne feuille de style est deja partie — ils s'afficheront simplement sans ces marges, ce qui est le signal qu'ils restent a faire.
Chercher le composant avant de chercher la marge
Devant flex flex-center mb-3, la question n'est pas « ou remettre ces 12 px » mais « qu'est-ce que cette barre ? ». Neuf fois sur dix elle a un nom dans le systeme, et le nom apporte l'espacement avec lui.
Quand vraiment rien ne convient
Ecrire la regle dans le CSS du composant concerne, avec un token d'espacement — jamais une classe utilitaire dans le balisage, jamais un style="margin-bottom:…". Si le cas se represente trois fois, c'est qu'il manque un composant : le signaler plutot que le contourner.
Ne pas recreer une feuille d'utilitaires « le temps de la migration »
C'est l'option qui a ete ecartee. Une feuille de transition ne s'enleve jamais : elle redevient le chemin le plus court, et l'ancien systeme repousse une classe a la fois. La decision est prise ; c'est le seul point de cette table ou il n'y a pas de marge d'appreciation.

Ce que cette table ne couvre pas

A traiter avant de considerer la migration complete
Les utilitaires d'espacement n'ont aucun equivalent
mb-1 a mb-4, mt-1 a mt-6, gap-2 a gap-4, flex, flex-center, grow — environ 300 usages. Le design system n'a pas d'utilitaires : l'espacement appartient aux composants, qui se placent correctement les uns par rapport aux autres. C'est le seul point de cette table qui demande une decision et pas une substitution. Deux voies : les supprimer au fur et a mesure (l'espacement vient alors du composant), ou conserver ces onze classes dans une petite feuille a part. Je recommande la premiere : la seconde reintroduit lentement l'ancien systeme.
Les trois zones ont été lues
Comptabilité (comptabilite.js, cinq vues : Journal général, Grand Livre, Balance, Bilan OHADA, Compte de résultat SYSCOHADA avec soldes intermédiaires) ; Administration (onze onglets, pas sept — utilisateurs, présence, rôles, niveaux d'accès, réinitialisations, compagnies, catégories, produits, paramètres, import, données) ; presence.js et import.js. Leurs classes sont dans la table, et le composant qui leur manquait existe.
Les tableaux comptables ont maintenant leur composant
pg-table--ledger et ses onze classes répondent aux quatre traits que ces tableaux ont et que les autres n'ont pas : ils se totalisent (<tfoot> stylé, que l'ancienne feuille laissait sans règle), ils ont une hiérarchie à trois niveaux dans le corps, ils s'équilibrent (pg-ledger-check, au-dessus du tableau), et une case vide y veut dire « pas de mouvement » plutôt que « donnée absente ». Voir la section Tableaux comptables du design system.
Lues dans le code, pas vues à l'écran
Je n'ai pas eu de session ouverte sur ces écrans : j'ai lu le HTML qu'ils produisent, pas le résultat avec de vraies données. Le balisage proposé est donc exact, mais le volume ne l'est pas forcément — un Grand Livre à quarante comptes ou une matrice de droits à quinze rôles peuvent demander un ajustement que seule la vraie donnée révélera. À regarder au moment de migrer ces modules, pas avant.
Les 375 classes reellement utilisees sont couvertes
Verifie a la generation : chaque classe de la colonne de gauche a ete trouvee dans le code telecharge, chaque classe de droite dans le CSS du design system. Les seules non listees sont neuf gabarits en fuite du type badge--, sans regle CSS associee.
